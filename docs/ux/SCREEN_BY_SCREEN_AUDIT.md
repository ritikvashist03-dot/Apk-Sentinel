# APK Sentinel static UX and accessibility audit

**Audit date:** 2026-08-22  
**Method:** source review of the current Compose shell, navigation, Home, language control, device-posture, installed-app, APK/link, network, privacy, resources, and shared design system, plus compile-plausible Compose instrumentation coverage for the owned UX surfaces. No emulator, device, TalkBack, or screenshot run was available in this checkpoint.

## Priority legend

| Priority | Meaning |
|---|---|
| P0 | Release blocker: can mislead about safety/privacy/capability or prevents an accessible required journey. |
| P1 | High-priority usability/accessibility gap: the core journey is likely difficult, inconsistent, or unreliable for a meaningful group of users. |
| P2 | Important refinement: should be addressed with the owning screen's next refactor and covered by regression tests. |

## What is already going in the right direction

- Copy generally avoids guaranteed-safety claims and states local-first limits.
- APK analysis exposes cancellation, partial-result wording, typed/resource-backed status, and an export explanation.
- Installed-app evidence avoids equating sideloading and old updates with malware, uses labelled toggle rows, selectable technical values, and retry while preserving prior results.
- Home now leads with current coverage, plain-language status states, one recommended Phone Checkup action, and four prominent plain tasks; recent activity remains secondary.
- Four labelled primary roots use drawable icons on compact navigation and a navigation rail on wider layouts.
- Privacy includes app-language selection, a refreshable local-data inventory with partial/truncation notices, and a persisted deletion receipt.
- Network setup offers Android notification-settings recovery when notification permission is not granted.
- `SectionTitle` receives a TalkBack heading semantic through the design system; onboarding progress and navigation state also expose semantics.

Those source-level strengths are foundations, not release evidence. The issues below must still be closed and tested.

## Required completion evidence per screen

Before a row above can be marked closed, its owner must supply:

1. a state inventory: initial, loading, content, partial, offline, stale, capability-needed, denied, error, retry, and active/stop/cleanup where relevant;
2. English, Hindi, pseudo-localised, 1.0x, and 2.0x screenshots at compact and expanded widths;
3. a TalkBack and keyboard task note covering title, status, primary action, error/recovery, and active-stop path;
4. semantic/screenshot test coverage for the primary task; and
5. runtime evidence for any engine/system state it renders. UI wording alone is not proof that a monitor, capture, rule, export, deletion, or certificate cleanup occurred.

## Audit limitations

This is deliberately a static audit. It cannot measure final colour contrast, actual TalkBack output, font fallback, focus order, timing, IME behaviour, Android permission dialogs, service state, privacy deletion, or network forwarding. Those need build and device/emulator validation after the owners integrate the current UI, localisation, and design-system changes.
